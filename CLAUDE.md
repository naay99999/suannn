bun --filter api typecheck             # API has no build step; typecheck instead
bun --filter storefront test           # bun test, preload tests/setup.ts

Run integration files one at a time with `--parallel=1` and `TEST_DATABASE_URL` set (they share and reset one database). ## Architecture

- **API composition.** `apps/api/src/index.ts` is the composition root: it loads config, builds every repository and service by hand (no DI container), and passes them as `AppDependencies` to `createApp` in `src/app.ts`, which mounts plugins and `create*Module` route modules. Route tests call `createApp` with their own dependency objects (fakes in `test/helpers/fakes.ts`), so a new service must be added to `AppDependencies`, `index.ts`, and the route tests that construct the app.
- **Store vs admin surfaces.** Most domains export a pair of modules: `/api/v1/store/*` (public or customer session, used by the storefront) and `/api/v1/admin/*` (staff session + permission, used by admin). Customer self-service is under `/api/v1/customer/*`; staff self-service auth under `/api/v1/auth/staff/*`.
- **Background work runs in the API process.** `index.ts` starts loops for reservation expiry, the order outbox (confirmation emails), guest-cart cleanup, and Stripe attempt/refund reconciliation, and drains them on shutdown. There is no separate worker.
- **Commerce invariants.** Stock is held by FIFO lot reservations (15 min); orders are confirmed only by verified Stripe webhooks or reconciliation, never by the success/cancel redirects. Inventory and refund mutations require an `Idempotency-Key`. Security-sensitive mutations write audit records in the same transaction.
- **Database.** Drizzle schemas live in `apps/api/src/database/schema/` (`auth.ts` is generated by Better Auth — regenerate with `auth:generate`, don't hand-edit); migrations in `apps/api/drizzle/`.
- **Typed clients.** The `api` workspace package exports `src/app.ts` directly, so frontends use `import type { App } from 'api'` and call `treaty<App>(…).api.v1` (`apps/*/src/lib/api.ts`). API route schema changes surface as frontend type errors; per-domain query hooks and helpers live in `apps/*/src/lib/<domain>/`.

## Media library (Cloudflare R2)

Product galleries and farm images come from a shared media library (`apps/api/src/modules/media`), not URL columns. Spec: `docs/superpowers/specs/2026-10-19-media-library-r2-design.md`; setup details: `apps/api/README.md` → "Media library".

- Uploads go through the API: sharp converts to WebP (`display` ≤2000px q80, `thumb` ≤480px q75, metadata stripped) and stores `media/{id}/display.webp` and `thumb.webp` in R2. Duplicate bytes return the existing item (SHA-256 dedup).
- URLs are derived at read time from `R2_PUBLIC_URL` and never stored, so changing the public domain is a config change only.
- Products reference media through `product_image` (ordered, max 12, first is the cover); farms use `cover_media_id` / `portrait_media_id`. FKs are `restrict`: an image in use cannot be deleted. Archiving a product or farm detaches its images.
- Publishing requires at least one image with alt text (products) or a cover with alt text (farms). Alt text lives on the media item, so editing it changes every usage.
- Env (`apps/api/.env.local`): `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_PUBLIC_URL` — all five or none (partial is a startup error). With none, uploads return 503 and image fields are empty, so products cannot be published.
- Use one bucket per environment. `R2_PUBLIC_URL` is the bucket's public URL (`https://pub-….r2.dev` for development; a custom domain in production — `r2.dev` is rate limited and not edge-cached). It is not the `*.r2.cloudflarestorage.com` S3 endpoint.
- `db:seed:demo` requires R2 and uploads demo images from `apps/storefront/public/images`.
- Local dev (2026-10-19): bucket `suann-dev`; the existing dev database was migrated in place and demo images were attached, instead of being reset.
