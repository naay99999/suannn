# Cart and COD Checkout Backend Design

**Status:** Proposed for written-spec review
**Scope:** `apps/api` database and HTTP API only
**Date:** 2026-09-27

## Goal and agreed scope

Let both signed-in customers and guests maintain a server-side cart and place a real cash-on-delivery (COD) order. The order must use authoritative product prices and FIFO inventory, preserve what the buyer agreed to, resist retries and concurrent stock changes, and support cancellation with a traceable restoration of stock before shipment. Staff need API access to process orders and record COD collection. The payment model must accommodate a later gateway without changing the order contract.

This phase does **not** build storefront or admin screens, a live payment gateway, card storage, coupons, tax breakdowns, carrier integration, returns after shipment, multiple warehouses, or a customer-facing shipment tracker. The existing storefront cart and admin orders pages contain example data and remain separate frontend work. Existing product, customer, address, auth, audit, and inventory IDs remain stable.

## Existing boundaries and chosen approach

Products owns catalog lifecycle and variant prices. Inventory owns lots, reservations, FIFO allocation, and physical movements. The new Cart module owns editable variant quantities. Orders owns checkout, immutable purchase snapshots, fulfillment status, and cancellation. Payments owns payment method/status and a provider interface; only the COD implementation is enabled in this phase. Orders orchestrates the existing `reserveInTransaction` and `confirmInTransaction` inventory ports, rather than calling the staff inventory HTTP routes. Extend the inventory actor context to distinguish authenticated customer, opaque guest checkout, staff, and background cleanup; the current `null` user ID remains reserved for background work and must not stand for a guest. Audit metadata records an order/guest principal ID, never the guest token or contact data.

Use an **order-first transaction**. A quote does not hold stock. COD order placement validates the quote, creates the order, reserves FIFO units, and confirms the reservation in one PostgreSQL transaction. This immediately subtracts the units from lot on-hand balances. The order records its reservation ID and exact allocation IDs so cancellation can restore the original lots. A future online method may create an order in `pending_payment` with a 15-minute hold; its signed, idempotent gateway callback will confirm or release that hold. No gateway adapter, webhook route, or online payment method is enabled now.

## Data model and invariants

- `cart`: UUID, one optional customer ID **or** one guest token hash, timestamps, and guest expiry. A signed-in customer has at most one active cart. A guest token is at least 256 random bits, is issued in an `HttpOnly`, `Secure` in production, `SameSite=Lax` cookie, and is never stored in plaintext. Guest carts expire 30 days after their last mutation. Expired carts are removed by a bounded cleanup job. The CORS and credentials policy must allow the documented storefront origin only.
- `cart_item`: cart ID, variant ID, integer quantity, timestamps, unique `(cart_id, variant_id)`. A cart has at most 50 lines and 99 units per variant. Cart stores neither price nor a claim to stock. A temporarily unavailable line may remain visible with a reason, but cannot be checked out.
- `commerce_settings`: a single active configuration row with nullable flat `shipping_fee_satang`, `checkout_enabled`, and a monotonically increasing version. Seed checkout disabled with no fee. Staff with `settings:read/update` may read or set the nonnegative shipping fee and enable COD checkout only after a fee is set. Settings changes are audited. No default free shipping is silently assumed.
- `order`: UUID, unique human-readable order number, nullable customer ID, guest access-token hash and token-version/nonce metadata when applicable, contact email and phone snapshots, complete Thai recipient/address snapshot, subtotal/shipping/total in satang, currency `THB`, payment method `cod`, fulfillment status, inventory reservation ID, quote fingerprint, creation/update timestamps, and idempotency metadata. An order is never repriced in place.
- `order_item`: order ID, immutable product ID, variant ID, SKU, product/variant names, unit, unit price in satang, quantity, and line total. Do not cascade-delete referenced catalog records.
- `order_item_allocation`: order item ID, inventory lot ID, reservation allocation ID, quantity, and restoration state. The sum per order item equals its quantity; allocations are the authority for cancellation restoration.
- `payment`: order ID, method, provider (`cod` now), amount/currency snapshot, payment status, optional provider reference, timestamps, and a uniqueness constraint preventing duplicate active payments for one order. Method/provider storage is extensible text validated by the enabled-method registry, not a database enum locked to `cod`. COD starts `awaiting_collection`, becomes `collected` only through an authorized staff command, and becomes `void` on pre-shipment cancellation. Provider-specific attempt/event data belongs behind a payment port and separate tables when a gateway is implemented. Do not store raw card or gateway credentials in these tables.
- `order_operation` and `order_event`: durable idempotency outcome and an append-only order/payment/fulfillment history. Operation scope is the authenticated customer ID or guest cart token hash plus command type; the same key and payload replay the same result, while reuse with another payload returns 409. Event/audit metadata uses IDs, amounts, and reason codes, not free-text secrets or full addresses.
- `outbox`: durable order-confirmation message intent, unique per order/event, with retry state and a bounded worker. It stores order references and template identifiers rather than raw guest access tokens. Email failure after commit never rolls back an order. The checkout response also returns the guest access token so an API client can retain it. Until the storefront order page exists, email may carry the order number and token as text; a link target is added when that page is built.

All monetary arithmetic uses integer satang with explicit upper bounds that prevent JavaScript precision loss and database overflow. Database checks enforce nonnegative totals and `subtotal + shipping = total`. Order creation, inventory movements, payment creation, cart clearing, event/audit writes, and outbox insertion commit or roll back together. No emails or external provider calls occur inside that transaction.

### Guest ownership and token lifecycle

The guest cart cookie identifies only a cart and cannot read an order. Guest order access uses an independent high-entropy token returned after checkout. Store only a verifier/hash and enough non-secret metadata to regenerate the token for the outbox worker under a versioned server secret; logs and audit records never include it. The API accepts the token in an `X-Order-Access-Token` header, not in a query string. A later storefront can place it in a URL fragment and move it into that header, avoiding server access logs and referrer leakage. Compare token verifiers in constant time. A missing, invalid, or expired token yields the same 404 response as an unknown guest order. The guest link remains valid through fulfillment and 30 days after the terminal order state; staff can reissue/revoke it with an audited command if recovery is needed. Customer account access always checks order ownership even when a guest token is present.

## Cart and checkout flow

1. `GET cart` returns current lines enriched from Products with live display price, sale status, and availability hint. Absolute-quantity `PUT cart/items/:variantId` and `DELETE` are naturally retryable. Mutations validate published, active variants and quantity limits; a later catalog change can mark a retained line unavailable. A customer login invokes an explicit atomic merge: sum matching quantities up to 99, keep at most 50 valid lines, skip invalid/unavailable lines with per-line reason codes, consume the guest cart token, and return the resulting cart and skipped lines. Repeating the merge cannot duplicate quantities.
2. `POST checkout/quote` reads a cart, current variants, and commerce settings; it returns item/price snapshots, subtotal, flat shipping fee, total, validation issues, and a short-lived signed fingerprint tied to cart contents, prices, settings version, owner, and expiry. Quote TTL is 15 minutes and is **not** an inventory hold. A quote is unavailable while checkout is disabled or shipping is unset. Client-supplied prices and totals are ignored.
3. `POST checkout/orders` requires a valid quote fingerprint, `Idempotency-Key`, `paymentMethod=cod`, contact email and phone, and a Thai delivery address. A signed-in customer may reference an owned saved address or send an inline address; a guest sends the inline address. The service normalizes and snapshots the chosen address. It locks the cart, involved product/variant rows in the inventory lock order, settings, and relevant lots, then recomputes prices and quote fingerprint. A stale quote, disabled sale, insufficient stock, or changed settings returns 409 with safe line-level codes and no order. The server never trusts client totals.
4. Within that same transaction, create the order and items, call FIFO reserve and confirm through transaction-aware inventory ports, persist exact allocation references, create the COD payment and order event, clear the cart, and enqueue confirmation intent. Repeated checkout with the same idempotency key returns the original order even though its cart was cleared; a changed payload conflicts. Checkout commits no partially filled order. The API returns the order and, for a guest, its access token on the original request and an exact idempotent replay.
5. Order confirmation email is sent from the outbox after commit. The worker retries with backoff and bounded concurrency. Replays do not enqueue duplicate confirmation messages. Delivery problems are observable to staff without leaking contact details in logs.

## Order, inventory, and payment lifecycle

Fulfillment progresses `placed -> processing -> packed -> shipped -> delivered`; `cancelled` is allowed from `placed`, `processing`, or `packed`. Only staff may advance fulfillment. A signed-in owner, the valid guest order token, or authorized staff may cancel before `shipped`. Shipment and cancellation race under an order row lock; exactly one transition wins. Customer and guest cancellation are no longer accepted after shipment.

Cancellation uses the original allocation records and locks the referenced product/variant/lot rows in the inventory command order. It adds a compensating, immutable stock movement for each lot and increases that lot's on-hand quantity once, clears the order's reversible allocation state, voids an uncollected COD payment, and writes an order event/audit entry in the same transaction. An expired or quarantined lot receives its physical units but remains ineligible for sale. To guarantee cancellation can restore stock despite the per-lot 1,000,000,000 limit, inventory count increases must leave room for units from cancellable, confirmed but unshipped orders; persist and enforce that reversible capacity at the lot level. Shipping releases this capacity without changing on-hand. Repeated cancellation replays the terminal outcome without a second movement. A shipped order needs a separate return process and is outside this phase.

COD collection is independent of fulfillment: staff records collection only for a non-cancelled order, with an amount equal to the order total and an idempotency key. Recording collection twice cannot double-count. A delivered order may temporarily remain `awaiting_collection` pending carrier reconciliation; a cancellation cannot occur once shipped. No online payment can be selected now.

The future gateway boundary is `PaymentProvider` plus payment attempts and verified provider events. A gateway method may create `pending_payment` orders with the existing 15-minute inventory hold, create provider requests **after** the order transaction, and resolve them through signature-verified, replay-safe webhooks. A successful callback must atomically confirm the held reservation and payment state; failure/expiry releases it. Late successes after hold expiry require explicit reconciliation/refund, never an untracked stock decrement. This is an interface and state-model requirement, not a request to implement a gateway now.

## HTTP contract and permissions

All routes use Elysia models, the exported `App` type, `{ code, message }` errors, and OpenAPI descriptions. Storefront mutations apply the existing storefront browser-origin guard; staff mutations apply the admin guard and permissions. Guest cart creation, checkout, and guest order access are rate-limited. Unknown fields and malformed IDs return 422. Unauthorized customer/staff access returns 401/403; guest order access uses the indistinguishable 404 rule above.

| Method and path | Access | Purpose |
| --- | --- | --- |
| `GET /api/v1/store/cart` | Customer session or guest cookie | Current cart and live line state |
| `PUT /api/v1/store/cart/items/:variantId` | Customer or guest | Set absolute quantity |
| `DELETE /api/v1/store/cart/items/:variantId` | Customer or guest | Remove line |
| `POST /api/v1/store/cart/merge` | Customer session + guest cookie | Merge and consume guest cart |
| `POST /api/v1/store/checkout/quote` | Customer or guest | Current quote; no stock hold |
| `POST /api/v1/store/checkout/orders` | Customer or guest | Place idempotent COD order |
| `GET /api/v1/store/orders` | Customer session | Own order history |
| `GET /api/v1/store/orders/:orderId` | Owner session or guest order token | Order detail |
| `POST /api/v1/store/orders/:orderId/cancel` | Owner session or guest order token | Cancel before shipment |
| `GET /api/v1/admin/orders` and `GET /api/v1/admin/orders/:orderId` | Staff `orders:read` | Paginated list/detail |
| `POST /api/v1/admin/orders/:orderId/fulfillment` | Staff `orders:update` | Advance fulfillment |
| `POST /api/v1/admin/orders/:orderId/cancel` | Staff `orders:update` | Cancel before shipment |
| `POST /api/v1/admin/orders/:orderId/collect-cod` | Staff `orders:update` | Record exact COD collection |
| `GET /api/v1/admin/commerce-settings` and `PUT /api/v1/admin/commerce-settings` | Staff `settings:read/update` | Read/set shipping fee and checkout switch |

If the fixed permission matrix lacks `orders:read/update`, extend it and test role-specific access rather than checking raw role names inside routes. Staff list endpoints use deterministic cursor pagination, default 50 and maximum 100. Order detail returns no guest token. The guest access token appears only in checkout creation/replay responses and the confirmation message. All commands that change an order, payment, or stock require an idempotency key of 1–128 visible non-whitespace ASCII characters, except naturally idempotent absolute cart updates/deletes.

## Verification and delivery

Use a dedicated PostgreSQL database ending in `_test` for migration and concurrency tests. Cover cart isolation/merge/expiry, token-cookie and origin policy, price/settings changes between quote and order, simultaneous checkouts competing for the last unit, exact idempotency replay, FIFO allocation snapshot, transaction rollback on audit/payment/outbox failure, guest order token ownership, cancellation/shipment race, exact lot restoration including expired/quarantined lots, count-versus-restoration capacity, COD collection, outbox retry, and typed HTTP/OpenAPI contracts. Assert that no client-provided amount, actor ID, or payment status can override server decisions. Run API typecheck, lint, unit and integration suites; report the two previously observed MFA integration failures separately if they recur, without changing MFA to make commerce tests pass.

Generate a new migration without editing earlier migrations. Document migration-before-deploy ordering, required guest-order signing secret, cookie/CORS settings, email worker, and the need to set shipping fee before enabling checkout. No real COD orders should be accepted until these are configured. Frontend integration, carrier integration, and gateway-specific operations are separate future work.
