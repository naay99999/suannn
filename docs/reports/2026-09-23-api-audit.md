# API audit: performance, code quality, and folder structure

Date: 2026-09-23  
Scope: `apps/api`, its database migrations and tests, and relevant workspace/CI configuration.  
Baseline: commit `3af1661` **plus the existing uncommitted working-tree changes**. No application code was changed during this audit.

## Assessment

The API has a sound feature-based foundation: thin Elysia route modules, dependency injection, explicit response schemas, separate database repositories, and meaningful authentication tests. Keep this architecture. The largest improvements concern database connection ownership, resource limits, and operational correctness rather than a broad folder rewrite.

There are **12 prioritized findings** below: two P1 and ten P2. P1 means address before significant production traffic; P2 means schedule a focused correction. Folder and cleanup suggestions are separate, lower-priority improvements. Performance findings describe code paths and scaling risks; this audit did not measure production throughput or latency.

### F01 — Avoid awaiting root-pool auth operations inside a held transaction

**Evidence:** `apps/api/src/modules/identity-claims/service.ts:43` opens a transaction and awaits its callback at line 63. Customer signup calls `auth.api.signUpEmail` inside that callback (`modules/auth/customer/service.ts:49–80`); invitation acceptance calls `auth.api.createUser` similarly (`modules/auth/invitations/service.ts:158–189`). Auth is constructed with the root database in `src/index.ts:31`, not the callback's `tx`.

**Impact:** Each outer transaction reserves a connection while auth needs another connection from the same pool. Enough concurrent distinct-email requests can occupy all connections and wait for work that cannot acquire one. The installed Postgres.js default pool maximum is 10 unless configuration overrides it. Password hashing also extends transaction and advisory-lock lifetime, including dummy hashes for occupied email addresses.

The ten-second retry deadline only runs between completed attempts; it cannot interrupt an attempt stalled while awaiting a connection. Same-email contention additionally retries a new transaction every 10 ms, adding database traffic while the first request is still working. Postgres.js documents transaction connection reservation in its [transaction guidance](https://github.com/porsager/postgres#transactions).

**Recommendation:** Redesign provisioning around explicit short reservation/finalization transactions and recoverable intermediate state, or use a supported transaction-aware auth integration. Preserve the email uniqueness and staff reservation guarantees. Move expensive work outside held transactions where safe. Add bounded provisioning concurrency, database wait/statement limits, and backoff with jitter. Increasing pool size alone only moves the threshold.

**Verify:** In an isolated database with a deliberately small pool, synchronize concurrent distinct-email signup and invitation acceptance requests. Assert bounded completion, uniqueness, recovery after failure, and a responsive health/request path. Record pool waits and transaction duration.

### F02 — Add an aggregate budget before expensive public signup work

**Evidence:** `modules/auth/customer/service.ts:37–43` limits the combination of email and IP. `modules/rate-limit/service.ts:25` hashes namespace, subject, and IP together. Changing email yields a fresh counter, even from the same IP. The route calls the internal auth API directly; the outer public signup route has no separate IP-only budget.

**Impact:** A caller can continuously submit new email addresses to trigger database writes, password hashing, and verification email delivery. Existing per-email throttling does not cap total work from that caller. Origin checks protect browser interactions but do not stop a scripted HTTP client from supplying an allowed Origin header.

**Recommendation:** Keep the email budget and add an independent per-client/IP budget before hashing or provisioning, plus a bounded global concurrency budget for expensive signup work. Configure trusted proxy handling deliberately: `shared/client-ip.ts:3–13` returns `unknown` when no trusted address is available, which otherwise merges unrelated callers into one bucket. An edge limit can complement application limits if it is explicitly configured and tested.

**Verify:** Submit many different emails from one resolved client address and confirm expensive operations stop at the aggregate budget. Check that unrelated clients remain independent under the intended deployment topology.

### F03 — Resolve authentication once per request

**Evidence:** Invitation list/create/resend/cancel routes enable both `staffAuth` and `permission` (`modules/auth/invitations/index.ts:24–65`). Both macros independently call `auth.api.getSession` (`plugins/auth/index.ts:134–164`). An in-process GET invitation-list probe returned 200 and counted **two** session lookups.

Each populated custom-session callback adds two explicit database reads (`plugins/auth/auth.ts:227–241`), even for customers; staff activity may add an update. The raw auth preflight also resolves a session before forwarding cookie-bearing `/get-session` requests to the handler, which performs session resolution again. Backup-code regeneration resolves in both the route macro and service.

**Impact:** Redundant database reads increase latency and pool pressure on routine authenticated traffic. The invitation route invokes four explicit custom-session reads across its two lookups, in addition to Better Auth's own work; this is not a measured total query count.

**Recommendation:** Make permission checking consume a single request-local authenticated result, or remove redundant `staffAuth` where `permission` supplies the required context and rejection semantics. Keep fresh authorization across requests; do not introduce a cross-request cache that delays revocation. Consider combining the two custom-session reads after confirming required freshness guarantees.

**Verify:** Count auth invocations and SQL queries on each protected route, while retaining missing-session, customer, restricted-staff, revoked-session, and permission-denial tests.

### F04 — Bound list queries and provide stable pagination

**Evidence:** `modules/auth/staff/repository.ts:16` lists all staff, `:124` lists all sessions for a user, and `modules/auth/invitations/repository.ts:32` lists all invitations, including historical resolved invitations. None has a limit or cursor.

**Impact:** Query work, response validation, serialization, payload size, and process memory grow with retained rows. Session listing also does not filter expired rows. The audit endpoint already caps its limit at 100, but offers no cursor for older records.

**Recommendation:** Add bounded page sizes and stable composite cursors, such as creation time plus ID for invitations. Support invitation-state filtering and define whether expired sessions belong in the result. Extend audit pagination when historical browsing is required. Evaluate matching indexes using representative `EXPLAIN (ANALYZE, BUFFERS)` plans; do not add speculative indexes solely from table size assumptions.

**Verify:** Seed representative history and assert maximum response size, deterministic ordering, and complete pagination when timestamps tie. Compare query plans for unfiltered and filtered access.

### F05 — Implement retention for application rate-limit rows

**Evidence:** `modules/rate-limit/repository.ts:13–59` inserts or resets a key's counter, but never removes expired keys. `database/schema/application-auth.ts:74–86` provides an expiry index. No application cleanup path was found. Revisiting a key resets its window; abandoned keys remain stored.

**Impact:** Unique email/IP/path combinations accumulate indefinitely. Traffic that rotates signup emails creates both fresh budgets and lasting rows. Storage and index maintenance costs increase over time.

**Recommendation:** Add a bounded, scheduled expiry purge using the existing index, with an explicit owner and metrics. Do not purge on every request. Independently review retention for Better Auth's own `rate_limit` table; this finding directly establishes only the application table's missing cleanup. Audit-log retention is already explicitly assigned to external operations in the README.

**Verify:** Confirm expired rows are deleted, live windows survive, and concurrent consume/purge operations preserve correct counts and expiry behavior.

### F06 — Validate the auth wrapper's parsed JSON before property access

**Evidence:** `plugins/auth/index.ts:37–39` casts parsed JSON to an object without checking its runtime shape. The two-factor branch follows the same pattern at lines 61–66.

**Reproduction:** With the real auth and error-handling plugins and a fake downstream auth handler, POST `/api/v1/auth/sign-in/email` with JSON body `null` returns 500 `INTERNAL_ERROR`. The malformed body `{` also returns 500. These failures occur in preflight before the downstream handler is called.

**Impact:** Invalid client input is reported as an application failure and generates error logs. It bypasses Better Auth's normal input-error handling.

**Recommendation:** Handle parsing failures explicitly and require a non-null JSON object before reading properties. Return the established safe 400/422 envelope. Apply the same handling to both two-factor challenge routes, with appropriately bounded request bodies.

**Verify:** Cover malformed JSON, `null`, arrays, primitives, empty objects, and valid objects. Assert invalid bodies do not reach identity lookups or auth handlers unnecessarily.

### F07 — Log actual response status and start timing earlier

**Evidence:** `plugins/request-logging.ts:19–32` starts timing in `onBeforeHandle` and records only `set.status`. A probe returning `Response.json(..., { status: 429 })` produced HTTP **429**, but the log recorded **200**. The raw auth handler and its preflight return Response objects, making this relevant to production routes.

**Impact:** Error-rate metrics derived from these logs can undercount failures. Timing omits earlier parsing/validation work, and requests rejected before `onBeforeHandle` have no start time and log zero duration. Elysia's [lifecycle documentation](https://elysiajs.com/essential/life-cycle) places the request hook before these stages.

**Recommendation:** Read the final Response status and initialize timing at the earliest request hook. Preserve timing/request correlation for validation failures and missing routes. Include the request ID in error logs as well as access logs.

**Verify:** Compare HTTP and logged status for native Response objects, domain errors, validation failures, 404s, and auth failures. Use a deliberately delayed earlier hook to verify timing includes it.

### F08 — Propagate request metadata into audit events

**Evidence:** `plugins/request-context.ts:16–23` generates the response/request-log ID and captures IP/user agent. Domain events instead call `crypto.randomUUID()` for `requestId`, for example `modules/auth/invitations/service.ts:81`, `modules/auth/customer/service.ts:76`, and `modules/auth/staff/repository.ts:193`. Those paths do not forward the captured IP/user agent.

**Impact:** Audit events cannot be reliably joined to the initiating request or to other events in that request. The schema suggests useful correlation exists, but the values are unrelated.

**Recommendation:** Pass a narrow audit context through command arguments, without passing full Elysia Context into services. Reuse the request ID and approved client metadata. Generate a separate operation ID for CLI actions. Also correct `revokeOwnSession`: it passes a session ID to the event helper while the helper fixes `targetType` to `user` (`staff/repository.ts:136–144, 185–195`).

**Verify:** Perform a mutation and assert that response header, access log, and audit event share the same ID. Check target type/ID consistency and absence of secrets.

### F09 — Distinguish expected signup outcomes from infrastructure failures

**Evidence:** `modules/auth/customer/service.ts:60–81` catches every exception from user creation, claim insertion, and audit insertion, performs another password hash, and returns the public accepted response without logging. Auth provisioning uses the root database independently of the claim/audit transaction.

**Impact:** Unexpected failures can look like successful requests operationally. A user may already be committed when claim/audit work fails. A later request can repair a missing customer claim through `IdentityClaimService`, but that does not recreate the lost `customer.created` event. Catching a SQL error inside the callback also does not restore an aborted PostgreSQL transaction.

**Recommendation:** Preserve the intended enumeration-resistant public response while distinguishing expected conflicts from infrastructure errors internally. Log sanitized failure categories with correlation, define idempotent reconciliation, and ensure transaction failures propagate to the transaction boundary. Avoid an extra expensive hash for arbitrary infrastructure failures unless required by a deliberate timing policy.

**Verify:** Inject failures after user provisioning, during claim insertion, and during audit insertion. Assert consistent retry behavior, appropriate internal signals, and eventual claim/audit reconciliation without revealing account existence.

### F10 — Bound background tasks and shutdown

**Evidence:** `src/index.ts:21–24` tracks an unbounded set of promises; shutdown awaits `app.stop()`, all background tasks, and `database.client.end()` without an application-level deadline (`:67–82`). `void task.finally(...)` creates a new promise that can reject without a handler if the supplied task rejects.

**Impact:** Slow external delivery or database work can delay shutdown indefinitely. Bursts can accumulate in-flight tasks. The email helper normally catches delivery failures, so the rejection concern applies to the generic runner contract and other/future tasks; it is not evidence that every email failure is unhandled.

**Recommendation:** Add bounded task concurrency, safe rejection handling, delivery/request deadlines, and a shutdown budget with guaranteed cleanup and an explicit timeout outcome. A durable outbox is already documented as deferred; keep that tradeoff explicit rather than presenting best-effort email as guaranteed delivery.

**Verify:** Exercise rejected and never-settling tasks and a delayed database close. Confirm the process completes shutdown within its configured budget and reports failures without leaking sensitive data.

### F11 — Provision a test database in CI

**Evidence:** `.github/workflows/quality.yml:19` runs `bun run check`. Root `package.json` includes `bun run test` in that command; the API test script runs unit and integration suites. The workflow defines neither a PostgreSQL service nor `TEST_DATABASE_URL`, which the integration preflight requires.

**Impact:** The checked-in workflow cannot complete the quality gate on an ordinary clean runner. Earlier stages may pass, but the integration preflight stops the pipeline and the subsequent build does not run. No historical CI run was inspected; this is a finding about the committed workflow configuration.

**Recommendation:** Provision an isolated PostgreSQL service with an `_test` database and health check, set `TEST_DATABASE_URL` for the job, and retain the reset safety checks. Avoid replacing the full test command with unit-only checks merely to make CI green. Keep database integration validation visible as its own step or job.

**Verify:** Run the workflow from a clean runner and confirm the integration suite actually executes, followed by the build stage.

### F12 — Make MFA audit guarantees explicit and complete

**Evidence:** `modules/auth/mfa/service.ts:27–53` activates staff and removes other sessions in a transaction without recording an activation event. `regenerateBackupCodes` changes credentials through Better Auth first and then records a standalone event (`:152–174`). The README broadly states that security mutations write their audit event in the domain transaction.

**Impact:** Staff activation leaves no corresponding audit record. Backup-code regeneration can succeed while its audit insert fails, leaving changed credentials and an error response without a durable event. The stated audit guarantee is stronger than these paths provide.

**Recommendation:** Add a staff-MFA activation action and record it in the existing activation transaction. For Better Auth-owned mutations, use supported transactional hooks or durable reconciliation to close the audit gap; explicitly document any remaining limitation. Make production-required audit dependencies mandatory rather than optional where silent omission would break the guarantee.

**Verify:** Confirm activation produces exactly one event and rolls back if mandatory auditing fails. Inject an audit failure after backup-code regeneration and verify the documented recovery/reconciliation behavior.

## Folder structure and clean-code assessment

The existing organization largely follows both API-specific repository instructions and Elysia's [feature-based structure guidance](https://elysiajs.com/essential/best-practice). Route instances act as controllers and services do not receive the full Elysia Context. Keep the `auth/{customer,staff,invitations,mfa}` grouping and independent `audit`, `email`, `identity-claims`, `rate-limit`, and `system` modules.

Recommended incremental changes, in order of value:

| Change | Reason | Scope |
| --- | --- | --- |
| Move `DatabaseStaffMfaStore` into `modules/auth/mfa/repository.ts` | MFA service currently mixes SQL persistence and workflow orchestration | Small extraction; preserve its interface |
| Define shared database/transaction types in `database/types.ts` | Many files repeat inferred database types; invitations currently imports transaction types from the identity-claims feature | Type-only cleanup |
| Move OpenAPI transformation helpers from `app.ts` to `plugins/openapi.ts` | Composition is obscured by summaries/filtering and `as never` schema casts | Preserve `createApp` and the exported `App` type |
| Introduce typed domain errors and one HTTP mapping | Error-message strings are an implicit protocol; owner-invariant mapping is duplicated in staff routes and the global handler | Gradual migration; preserve public codes |
| Separate unit/integration test directories when next reorganizing tests | Manually enumerated test scripts can omit newly added files | Update scripts atomically; preserve database preflight |
| Correct root guidance about testing | Root and API-specific instructions currently disagree | Documentation only |

A modest target layout is sufficient:

```text
apps/api/
  src/
    app.ts                     # Elysia composition and App export
    index.ts                   # startup, dependency wiring, shutdown
    config/
    database/
      client.ts
      types.ts                 # proposed common DB/transaction types
      schema/
    modules/
      auth/
        customer/
        invitations/
        mfa/
          index.ts
          model.ts
          service.ts
          repository.ts        # proposed extraction
        staff/
      audit/
      email/
      identity-claims/
      rate-limit/
      system/
    plugins/
      auth/
      openapi.ts               # proposed extraction
      ...
    shared/
  drizzle/
  test/
    unit/                      # optional later organization
    integration/
    helpers/
```

Do not add repositories to modules with no persistence or introduce traditional controller classes. Generated auth schema formatting differs from handwritten style; maintaining reproducible generation is more valuable than manually reformatting generated output. Avoid a broad folder migration alongside transaction fixes.

## Existing strengths to preserve

- Application construction is separate from listening, enabling in-process route tests and Eden Treaty type exports.
- Named Elysia plugins, inline handlers, and explicit response models keep composition and route contracts understandable.
- SQL uses parameterized Drizzle/query templates. Application rate-limit increments are atomic database upserts.
- Identity claims, unique indexes, transaction locks, and invitation retry tests show deliberate handling of races.
- Server-owned account fields, auth endpoint allowlisting, role checks, and restricted MFA onboarding are explicit.
- Staff session activity writes are already throttled to once per minute with compare-and-update semantics.
- Email dependencies are injectable and delivery errors are handled; best-effort delivery is documented.
- Integration helpers require a dedicated database and check its name before resetting schemas.

## Suggested implementation order

1. Resolve F01/F02 together: bound signup work and correct transaction/pool ownership without weakening identity guarantees.
2. Repair CI database setup (F11) so integration checks protect subsequent changes.
3. Fix the reproduced issues F03/F06/F07 with focused route tests.
4. Address F08/F09/F12 as one audit consistency and failure-recovery effort.
5. Add pagination, rate-limit retention, and bounded shutdown (F04/F05/F10).
6. Make small structural extractions while touching the relevant files; avoid a standalone architectural rewrite.

Before claiming performance improvement, establish a reproducible baseline for signup, authenticated session reads, invitation listing, and contention. Measure p50/p95/p99 latency, requests completed, error rate, SQL count, pool wait, lock duration, process memory, and response bytes at realistic data volumes. Compare the same workload after each change. This report establishes risks and concrete defects, not benchmark results.
